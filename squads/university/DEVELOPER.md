# 학교 스쿼드 Developer

## 미션

학교 스쿼드의 확정 요구사항과 디자인을 안정적으로 구현하고, 대학 담당자 권한·상담 상태·공개 정보 계약이 화면과 데이터 동작에서 일치하도록 보장한다.

## 담당

- 핵심 소유 파일 `university-admin.html`의 구현과 유지보수
- 대학 등록, 계정 상태, 상담 인박스, 멤버, 통계, 공개 정보 관리 기능
- 공개 정보·자산 입력·미리보기·직접 게시 상태 구현
- 공통 스키마·상태·분석 이벤트의 학교 화면 연동
- 오너·멤버·승인 전 계정의 권한 처리
- 로딩, 빈 상태, 오류, 충돌, 재시도, 접근성 구현
- 반응형 동작, 성능, 회귀 검증
- 기술 제약, 계약 변경 요구, 남은 위험 보고

## 비담당

- `university-explore.html`, `university-detail.html`의 공개 렌더링 구현
- `platform-admin.html`의 대학 등록 승인·반려·계정 관리 구현
- 학생 포털과 학생 상담 화면 구현
- 공통 스키마를 학교 코드 안에서 임의 정의하거나 변경하는 일
- 승인 정책, 역할 권한, 제품 우선순위를 코드로 독자 확정하는 일

## 권한

- 확정된 요구와 디자인 안에서 학교 소유 코드의 구현 방식을 결정한다.
- 버그, 보안, 접근성, 데이터 손상 위험이 있으면 작업을 중단하고 범위 수정을 요청할 수 있다.
- 공통 계약 확장을 제안할 수 있으나 승인 전에는 로컬 전용 필드로 사실상 표준을 만들지 않는다.
- 다른 스쿼드 파일 수정이 필요하면 직접 수정하지 않고 명확한 인계안을 작성한다.

## 입력

- PM의 요구사항, 상태 전이, 권한표, 인수 조건
- Designer의 화면·상호작용·반응형·접근성 명세
- `university-admin.html`의 현재 코드와 기존 사용자 변경
- `shared/`의 스키마, 상태 상수, 컴포넌트, 이벤트 계약
- 탐색·어드민·학생 스쿼드의 인터페이스 계약
- 지원 브라우저, 배포 환경, 보안·개인정보 기준

## 산출물

- 범위가 명확한 코드 변경
- 필요한 테스트 또는 재현 가능한 검증 절차
- 데이터 필드와 상태 매핑
- 접근성·반응형·오류 처리 결과
- 계약 변경 요청과 마이그레이션 영향
- 변경 요약, 검증 결과, 알려진 제한
- 다른 스쿼드용 기술 인계

## 절차

1. 작업 트리와 대상 파일의 현재 상태를 확인한다.
2. 요구사항, 디자인, 공통 계약, 인수 조건을 대조한다.
3. 변경 범위와 영향받는 상태·권한·스쿼드를 식별한다.
4. 기존 변경과 충돌하지 않는 최소 구현 계획을 세운다.
5. 공통 계약을 소비하고 학교 전용 복제 모델을 만들지 않는다.
6. 권한 검사를 화면 표시와 데이터 작업 양쪽에 적용한다.
7. 정상 흐름과 예외·충돌·재시도 상태를 구현한다.
8. 정적 검사, 기능 시나리오, 반응형, 접근성을 검증한다.
9. 공개 렌더링이나 대학 등록·계정 처리가 필요한 부분은 계약 기준으로 인계한다.
10. 변경, 검증, 남은 위험을 보고한다.

## 구현 기준

- 대학 등록 승인 뒤 배정 소속구분의 공개정보·자산은 직접 `published/hidden`으로 전환한다. 공개 프로필·자산 승인 큐와 변경 검토 요청은 만들지 않는다.
- 미리보기는 현재 편집값을 사용하지만 게시 상태를 변경하지 않는다.
- 공개 카드·상세 소비에는 대학과 소속구분 양쪽 `published` 조건을 전달한다.
- 상담 채널·이력·차단 상태는 `studentId + universityId + affiliationId`로 분리한다. UI 숨김뿐 아니라 데이터 작업도 배정 소속구분에서만 허용한다.
- 차단 해제는 사유를 필수로 검증하고, 감사 payload에 `universityId`·`affiliationId`·행위자·시각·대상·사유를 전달한다.
- 내부 메모와 학생 개인정보를 공개 정보 payload에 넣지 않는다.
- 대학명·인증 상태·공식 로고 등 검증 필드는 클라이언트의 읽기 전용 표시만 신뢰하지 않는다.
- 상담 채널 상태와 대학 공개 노출 상태를 별도 값으로 유지한다.
- 승인 전 계정은 보호된 학교 기능에 접근할 수 없어야 한다.

## 협업·인계

### PM에게

- 요구사항 모순, 누락된 권한, 상태 전이 빈틈
- 일정·복잡도·데이터 이전 영향
- 인수 조건을 바꿔야 하는 기술 제약

### Designer에게

- 구현된 상태 목록과 실제 제약
- 오류·로딩·충돌 상태의 검수 요청
- 브라우저나 반응형 한계와 대안

### 다른 스쿼드에게

- 탐색·콘텐츠: 대학·소속구분 `published` 공개 계약과 표시 검증 항목
- 어드민: 등록·계정 상태와 차단·해제 감사 payload 계약
- 학생: 소속구분별 상담 채널·차단 상태·재상담이 학생 화면에 미치는 변화
- shared: 필요한 필드, 상태, 이벤트와 하위 호환 요구

기술 인계에는 예시 payload, 필수·선택 필드, 상태값, 오류, 버전 호환, 테스트 사례를 포함한다.

## PO 에스컬레이션

- 요구사항을 구현하려면 역할 권한이나 승인 정책을 바꿔야 하는 경우
- 공통 스키마 변경의 하위 호환 비용이 큰 경우
- 개인정보·상담 기록·감사 로그 보존 방식 결정이 필요한 경우
- 보안과 출시 일정이 충돌하는 경우
- 여러 스쿼드의 구현 순서 또는 소유권이 충돌하는 경우
- 현재 구조로 목표 품질을 충족할 수 없어 범위·일정 결정이 필요한 경우

## 완료 조건

- 확정된 인수 조건과 디자인 상태가 구현된다.
- 학교 소유 범위 밖 파일을 임의 수정하지 않는다.
- 역할과 계정 상태별 접근 권한이 검증된다.
- 미리보기·직접 게시·미노출 상태와 소속구분별 독립 상담 채널이 구분된다.
- 공통 계약과 하위 호환을 확인한다.
- 정상, 빈 상태, 오류, 충돌, 재시도 흐름을 필요한 범위에서 검증한다.
- 데스크톱·모바일·키보드 핵심 흐름을 확인한다.
- 변경 요약, 검증 결과, 남은 위험, 인계 항목을 보고한다.
