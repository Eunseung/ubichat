# 학교 스쿼드

대학 담당자가 ubichat에 입점하고, 공개 대학 정보를 준비하며, 학생 상담을 운영하는 경험을 책임진다.

## 스쿼드 구성

| 역할 | 에이전트 문서 | 핵심 책임 |
|---|---|---|
| Product Manager | `PRODUCT_MANAGER.md` | 문제 정의, 정책 구체화, 우선순위, 인수 조건 |
| Designer | `DESIGNER.md` | 대학 담당자 UX, 정보 구조, 상태·오류·반응형 설계 |
| Developer | `DEVELOPER.md` | 학교 소유 화면 구현, 계약 연동, 품질 검증 |

역할이 명시되지 않은 학교 스쿼드 세션은 Product Manager가 먼저 요청을 분류한다. 디자인과 구현이 함께 필요한 작업은 `PM → Designer → Developer` 순서로 인계한다.

## 즉시 실행

- [2026-07-29 P1 즉시 실행](./IMMEDIATE_ACTIONS_2026-07-29.md)을 최신 작업 기준으로 함께 읽는다.

## 소유 영역

- 대학 등록 신청과 승인 대기·반려·재신청 경험
- 대학 오너·멤버의 로그인과 권한별 경험
- 상담 인박스, 상담 시작·담당·이관·종료, 내부 메모
- 멤버 초대와 대학 조직 운영
- 상담 통계와 운영시간·상담 채널 상태
- 공개 대학 정보·자산의 입력, 미리보기, 직접 게시·미노출
- 공통 계약의 소속구분별 공개 생산 데이터 관리

현재 핵심 소유 파일은 프로젝트 루트의 `university-admin.html`이다.

## 다른 스쿼드와의 경계

| 대상 | 학교 스쿼드 책임 | 상대 스쿼드 책임 |
|---|---|---|
| 공개 대학 정보 | 배정 소속구분의 입력, 미리보기, `published/hidden` 직접 게시 | 탐색·콘텐츠 스쿼드가 확정 공통 계약을 렌더링 |
| 승인·노출 | 대학 등록 승인 뒤 공개정보·자산을 직접 게시 | 어드민 스쿼드는 대학 등록·계정 발급·플랫폼 계정 상태를 관리하며 공개 자산을 사전 승인하지 않음 |
| 상담 | 대학 담당자의 인박스와 응대 운영 | 학생 스쿼드가 학생의 상담 시작·채팅·재상담 경험 관리 |
| 데이터 구조 | 요구사항과 확장 제안 | 공통 계약은 `shared/`에서 정의하고 PO가 충돌을 조정 |
| 사업 방향 | 현장 요구와 지표 제안 | Product Owner가 제품 방향, 우선순위, 공통 정책을 최종 결정 |

학교 스쿼드는 공개 탐색 화면을 복제하거나 직접 소유하지 않는다. 대학 등록 승인 뒤 배정 소속구분의 공개 상태를 직접 관리한다. 공통 스키마를 학교 화면 내부 형식으로 독자 변경하지 않는다.

## 공개 정보 흐름

1. 대학 등록이 승인된 뒤, 배정 소속구분 구성원이 수정 가능한 정보를 입력한다.
2. 공통 스키마 기준으로 공개 화면 미리보기를 생성한다.
3. 구성원이 해당 소속구분을 `published` 또는 `hidden`으로 직접 전환한다.
4. 대학과 해당 소속구분이 모두 `published`이면 탐색·콘텐츠 영역이 공개 데이터를 렌더링한다.

미리보기는 게시 상태를 바꾸지 않는다. 공개 프로필·자산 승인 큐나 변경 검토 요청은 없다.

## 현재 목업 기준

- 승인 전 대학 계정은 상담 인박스와 운영 메뉴를 이용할 수 없다.
- 상담 채널은 `studentId + universityId + affiliationId`별로 독립한다. 관계자는 배정 소속구분 채널만 열람·응대하고, 복수 소속구분 권한자는 각 채널을 모두 본다.
- 상담 시작 시 담당자가 정해지며, 진행 중 상담의 현재 담당자가 종료한다.
- 오너는 멤버 초대·관리 권한을 가진다.
- 대학명·인증 상태는 플랫폼 확인 정보이며, 로고·배경·사진·브로셔는 배정 소속구분 구성원이 직접 수정·게시한다.
- 상담 채널 상태는 공개 대학 소개의 노출과 분리한다.

학생 차단·차단 해제는 같은 소속구분 채널에만 적용한다. 해제 사유는 필수이며, 다른 소속구분 상담에는 영향을 주지 않는다.

## 세션 시작 방법

1. 이 `README.md`와 `AGENTS.md`를 읽는다.
2. 요청에 맞는 역할 문서 하나를 읽는다.
3. 프로젝트 루트의 최신 기획 기준과 `shared/` 계약을 확인한다.
4. 현재 상태, 결정할 사항, 영향받는 스쿼드를 짧게 선언한다.
5. 소유 경계를 넘는 변경은 직접 수행하지 않고 인계안을 만든다.

세션 예시:

- “학교 PM 역할로 공개정보 변경 검토 정책을 구체화해줘.”
- “학교 Designer 역할로 상담 인박스의 미배정 상태를 설계해줘.”
- “학교 Developer 역할로 승인 대기 화면을 구현하고 검증해줘.”

## 공통 완료 기준

- 대학 담당자가 해야 할 일과 다음 상태를 이해할 수 있다.
- 최고관리자·소속구분 관리자·멤버의 배정 소속구분 권한 차이가 일관된다.
- 로딩, 빈 상태, 오류, 권한 없음, 등록 검토 중, 반려 상태가 정의된다.
- 공통 스키마와 상태값을 임의로 복제하지 않는다.
- 학생·탐색·어드민 화면에 미치는 영향과 인계 항목이 기록된다.
- 변경 범위에 맞는 기능·반응형·접근성 검증이 완료된다.
